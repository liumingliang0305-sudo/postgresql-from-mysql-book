# 前言：不要把 PostgreSQL 当成换了语法的 MySQL

从 MySQL 转向 PostgreSQL，最容易犯的错误不是语法写错，而是沿用原来的判断方式。

例如，MySQL 开发者常把“表”直接对应到磁盘上的某种主键有序结构，把 `REPEATABLE READ` 当作事务的默认起点，把 `AUTO_INCREMENT` 当作编号生成器，把 `EXPLAIN` 的 `rows` 当作优化器估算的核心入口。这些经验并非无效，但放到 PostgreSQL 中，需要重新解释。

PostgreSQL 的普通表是堆表，行位置会变化；更新通常产生新的行版本，旧版本由 VACUUM 回收；默认隔离级别是 Read Committed，一个事务中的两条查询可能使用不同快照；序列独立于事务，即使事务回滚，已经取出的序列值通常也不会归还；优化器不仅依赖单列统计信息，还会在顺序扫描、位图扫描、不同连接算法和并行路径之间做成本比较。

这些差异最终会落到真实问题上：

- 为什么删除大量数据后，表文件没有缩小？
- 为什么一条普通查询会挡住表结构变更？
- 为什么明明有索引，优化器仍然选择顺序扫描？
- 为什么把 `work_mem` 调大后，服务器反而更容易内存不足？
- 为什么复制槽能保护订阅端，却也可能占满主库磁盘？

本书从这些问题出发。每章先描述现象，再建立机制模型，最后给出检查方法和工程结论。读者不需要先成为 DBA，但需要能读懂 SQL、事务和索引的基本概念。

## 本书不做什么

第一，不追求覆盖所有 SQL 语法。语法可以查手册，真正影响设计的差异必须形成心智模型。

第二，不把参数调优写成固定公式。数据库负载由并发数、数据分布、查询形态和硬件共同决定，脱离观测谈参数没有意义。

第三，不把高可用等同于安装某个组件。复制、故障检测、仲裁、切换、客户端重连和数据一致性共同构成高可用。

## 怎样使用这本书

建议准备一个可以随时重建的 PostgreSQL 实例，亲自执行书中的示例。观察 `EXPLAIN (ANALYZE, BUFFERS)`、`pg_stat_activity`、`pg_locks` 和统计视图，比记住结论更重要。

每章末尾的问题不是考试题，而是用来检查模型是否闭合。如果答案只能靠背诵命令，说明还没有真正理解这一章。

# 第五部分：把数据模型交给数据库

## 第 21 章：约束为什么不该只写在应用里？

应用校验可以给出友好提示，却不能独自保护并发写入、离线脚本、数据修复和未来服务。数据库约束是所有写入路径共享的最后一道规则。

### 用最接近业务事实的约束

```sql
CREATE TABLE booking (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL REFERENCES room(id),
    starts_at timestamptz NOT NULL,
    ends_at timestamptz NOT NULL,
    status text NOT NULL,
    CONSTRAINT ck_booking_time CHECK (starts_at < ends_at),
    CONSTRAINT ck_booking_status
        CHECK (status IN ('pending', 'confirmed', 'cancelled'))
);
```

`NOT NULL` 表达必填，`CHECK` 表达单行规则，`UNIQUE` 表达候选键，外键表达对象间引用。约束名称应稳定，便于应用识别冲突并转换成业务错误。

### “先查有没有”不能替代唯一约束

两个事务可能同时查询不到同一邮箱，然后同时插入。只有唯一约束能够在并发提交路径上裁决冲突。应用可先查以改善提示，但正确性仍由约束保证。

### 延迟约束解决的是事务内顺序

部分唯一约束和外键可以声明为 deferrable，在事务结束时检查，适合互换位置、批量调整图关系等场景。

```sql
ALTER TABLE seat_assignment
ADD CONSTRAINT uq_flight_seat
UNIQUE (flight_id, seat_no)
DEFERRABLE INITIALLY DEFERRED;
```

延迟检查不是取消检查；冲突会在提交时暴露，应用仍要处理提交失败。

### 给大表加约束要分离“开始保护”和“验证历史”

外键与部分 CHECK 约束可以先以 `NOT VALID` 创建，使新写入受约束，再择机验证已有数据：

```sql
ALTER TABLE payment
ADD CONSTRAINT fk_payment_order
FOREIGN KEY (order_id) REFERENCES orders(id)
NOT VALID;

ALTER TABLE payment
VALIDATE CONSTRAINT fk_payment_order;
```

这能降低首次上线的锁与扫描影响，但验证仍会消耗 I/O，且创建约束本身也要评估锁。

### 排斥约束表达“不能重叠”

唯一约束只能判断相等。时间段、空间范围等“不相交”规则可使用 exclusion constraint：

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE booking
ADD CONSTRAINT no_room_overlap
EXCLUDE USING gist (
    room_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
)
WHERE (status = 'confirmed');
```

**本章结论**：应用校验负责体验，数据库约束负责事实。能够由声明式约束表达的规则，不应只藏在某个服务的代码路径里。

**思考题**：给已有十亿行表添加外键时，为什么 `NOT VALID` 加后续验证通常比一次完成更容易控制风险？

## 第 22 章：JSONB、数组和范围类型什么时候值得用？

PostgreSQL 提供丰富类型，不代表关系模型已经过时。选择标准应是数据语义和访问模式，而不是“少建几张表”。

### JSONB 适合边界内的半结构化属性

```sql
CREATE TABLE product_event (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id bigint NOT NULL,
    kind text NOT NULL,
    attributes jsonb NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

事件来源多、少量属性随类型变化时，JSONB 很合适。核心关联键、金额、状态和高频过滤列仍应保留为类型明确的普通列，便于约束、统计和索引。

JSONB 每次更新通常生成新的行版本和新的 JSON 值。把频繁变化的小字段埋进巨大文档，会增加写放大。索引前先列出操作符：包含 `@>`、键存在 `?`、JSON path，所需索引并不相同。

### 数组适合“整体属于一行”的小集合

标签、少量权限标记可用数组：

```sql
CREATE INDEX idx_article_tags ON article USING gin (tags);
SELECT * FROM article WHERE tags && ARRAY['postgresql', 'database'];
```

如果数组元素有自己的属性、生命周期、外键关系或需要频繁单独更新，应拆成关联表。数组不是逃避多对多建模的捷径。

### 范围类型把边界语义变成一等对象

```sql
SELECT tstzrange(
    '2026-09-10 09:00+08',
    '2026-09-10 10:00+08',
    '[)'
);
```

`[)` 表示包含起点、不包含终点，使相邻时间段不重叠。范围类型支持包含、相交、相邻等操作，也能与 GiST 索引和排斥约束组合。

### 类型能力必须配套治理

采用复合类型前，团队要约定：允许的结构、如何演进、如何索引、如何做统计、哪些字段可以进入接口契约。否则“灵活”会逐渐变成无法约束的数据堆积。

**本章结论**：JSONB 解决受控的结构变化，数组表达行内小集合，范围类型表达连续区间。核心关系和高频业务条件仍应显式建模。

**思考题**：商品属性都存入 JSONB 后，为什么按品牌、类目和价格做复杂筛选可能比普通列更难优化？

## 第 23 章：窗口函数、CTE 和 LATERAL 能解决什么问题？

很多应用先查询一批数据，再在内存中分组、排序和补查。PostgreSQL 的分析型 SQL 可以让数据库在一次计划中完成这些步骤。

### 窗口函数保留明细，同时计算组内结果

查询每个客户最近三笔订单：

```sql
SELECT customer_id, id, created_at, total_amount
FROM (
    SELECT o.*,
           row_number() OVER (
               PARTITION BY customer_id
               ORDER BY created_at DESC, id DESC
           ) AS rn
    FROM orders AS o
) AS ranked
WHERE rn <= 3;
```

窗口函数与 `GROUP BY` 不同：它不会把多行折叠成一行。累计值、移动平均、排名和前后行比较都适合窗口表达。

### CTE 首先是可读性和递归工具

```sql
WITH paid_order AS (
    SELECT * FROM orders WHERE status = 'paid'
)
SELECT customer_id, sum(total_amount)
FROM paid_order
GROUP BY customer_id;
```

现代 PostgreSQL 可以内联满足条件、只引用一次且无副作用的 CTE。`MATERIALIZED` 强制先计算并保存，`NOT MATERIALIZED` 倾向允许内联。不要沿用“CTE 必然是优化屏障”的旧结论，也不要无依据地强制物化。

递归 CTE 适合树、图遍历和层级路径，但要设置终止条件并考虑环检测。

### LATERAL 让右侧子查询引用左侧当前行

查询每位客户最近一笔订单：

```sql
SELECT c.id, last_order.id, last_order.created_at
FROM customer AS c
LEFT JOIN LATERAL (
    SELECT o.id, o.created_at
    FROM orders AS o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 1
) AS last_order ON true;
```

配合 `(customer_id, created_at DESC, id DESC)` 索引，这种写法可以对每个客户做小范围定位。若外表有数百万行，它也可能变成数百万次内层查找，仍要看实际计划。

### 集合化不等于把所有逻辑塞进一条 SQL

一条过度复杂的 SQL 会增加规划、调试和回归难度。边界应看数据是否需要在数据库内部高效关联，以及操作是否需要原子一致。外部 API、复杂流程编排和不可撤销副作用不适合隐藏在巨型 SQL 中。

**本章结论**：窗口函数处理组内分析，CTE 组织或递归数据流，LATERAL 表达逐行相关子计划。最终选择仍由数据规模和执行计划验证。

**思考题**：每位客户取最近订单时，窗口函数方案和 LATERAL 方案分别更适合什么规模的外表与内表？

## 第 24 章：函数、触发器和扩展的边界在哪里？

PostgreSQL 可以把很多逻辑放进数据库。能力越强，越需要明确边界，否则业务行为会散落在应用、函数和触发器之间。

### 函数适合靠近数据的确定性计算

SQL 函数适合封装可复用查询和计算。函数的波动性标记会影响优化器判断：

- `IMMUTABLE`：同样输入永远得到同样结果；
- `STABLE`：单条语句期间结果稳定；
- `VOLATILE`：每次调用都可能变化，也是默认值。

错误标记为 `IMMUTABLE` 可能让优化器提前折叠或索引错误结果。读取表、当前时间、配置或会话状态的函数通常不满足不可变条件。

### 存储过程适合显式的服务端操作入口

过程通过 `CALL` 执行，与函数在事务控制和调用方式上不同。它适合管理型批处理，但不应把不可观测的长事务隐藏在过程里。

### 触发器只保留必须覆盖所有写入路径的逻辑

审计字段、派生数据或跨入口必须执行的校验可能适合触发器。发送 HTTP 请求、复杂工作流和耗时计算不适合放在同步触发器里，因为调用方只会看到一次普通写入变慢或失败。

触发器要记录在数据字典和变更流程中，测试直接 SQL、批量导入、复制和恢复时的行为。

### `SECURITY DEFINER` 是权限边界

以所有者权限执行的函数可以提供受控能力，但必须固定安全的 `search_path`、限制 `PUBLIC` 执行权限，并避免动态拼接未验证标识符。否则攻击者可能通过同名对象遮蔽劫持调用。

### 扩展把能力装进数据库，也进入升级链

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

全文、模糊匹配、地理、时序等能力可以由扩展提供。采用前要确认版本兼容、托管平台支持、备份恢复、主备安装和升级路径。扩展不是复制一个 SQL 文件那么简单。

**本章结论**：靠近数据、需要事务一致且能清楚观测的逻辑适合进入数据库；跨系统流程和不可撤销副作用留在应用层。

**思考题**：一个触发器在提交前调用第三方接口，数据库事务回滚时会发生什么不一致？

## 第 25 章：分区表能解决大表的所有问题吗？

分区把一个逻辑表映射到多个物理分区。它最擅长的是按分区键裁剪扫描、快速装卸数据和分散维护窗口，而不是自动加速每条查询。

### 分区键必须来自访问和生命周期

```sql
CREATE TABLE event (
    tenant_id bigint NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload jsonb NOT NULL
) PARTITION BY RANGE (occurred_at);

CREATE TABLE event_2026_09
PARTITION OF event
FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

如果大多数查询都带时间范围，按时间分区可触发 partition pruning；过期数据可以通过 detach/drop 分区快速处理。若查询只按 `tenant_id`，时间分区未必减少扫描。

### 分区过多也有成本

大量细碎分区会增加规划、元数据、autovacuum 调度和日常管理成本。分区粒度应由单分区大小、查询时间窗、数据保留周期和维护能力共同决定，而不是固定“每天一张”。

### 唯一性受分区边界限制

要在分区表上建立跨所有分区有效的唯一或主键约束，约束键通常必须包含全部分区键列。PostgreSQL 没有一个独立的全局唯一索引替你跨分区裁决任意键。

若业务要求全局唯一订单号，却按时间分区，可以把时间纳入主键、使用外部生成且概率唯一的 ID，或建立单独的全局键登记表。每种选择都有一致性和写入成本。

### 分区不能替代索引和 VACUUM

每个分区仍是普通表，需要自己的索引、统计信息和 VACUUM。分区内查询若没有合适索引，裁剪后仍可能扫描大量数据；热点分区仍会产生 dead tuple 和膨胀。

上线新分区要自动化，并提前处理默认分区中的冲突数据。附加已有表时，预先建立能证明边界的 CHECK 约束，可减少不必要的验证扫描与锁时间。

**本章结论**：分区解决数据裁剪与生命周期管理，不解决错误查询、缺失索引或无限增长的单行热点。先确定分区键能否出现在主要谓词中。

**思考题**：查询几乎从不带时间条件时，把表按月分区为什么可能让维护更复杂，却没有明显查询收益？

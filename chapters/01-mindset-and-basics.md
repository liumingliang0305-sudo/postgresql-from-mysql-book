# 第一部分：先换一套坐标系

## 第 1 章：一条 SQL 在 PostgreSQL 中是怎样执行的？

下面这条查询看起来没有特别之处：

```sql
SELECT id, title
FROM article
WHERE author_id = 42
ORDER BY published_at DESC
LIMIT 20;
```

但 PostgreSQL 接收到它以后，并不是简单地“找到索引并读取数据”。一条语句大致会经过解析、分析、重写、规划和执行五个阶段。

解析器把文本变成语法树；分析阶段解析表、列、操作符和数据类型；重写系统应用视图与规则；规划器枚举可行路径并估算成本；执行器按照最终计划拉取数据。客户端通常由后端进程或后端执行上下文服务，而共享缓冲区、WAL 缓冲区和后台进程共同维护实例状态。

与 MySQL 对比时，最重要的不是记住进程名称，而是理解三个边界。

### 客户端连接不是“轻量线程”

传统 PostgreSQL 架构中，每个客户端连接对应一个服务端后端进程。连接会占用内存和调度资源，因此不能把 `max_connections` 当作吞吐量旋钮。高并发短连接通常需要连接池，后文会专门讨论。

### 优化器选择的是成本最低，不是代码最短

规划器会比较顺序扫描、索引扫描、只读索引扫描、位图扫描以及不同连接顺序。成本是抽象单位，受统计信息、页面读取成本、CPU 成本、并行度和缓存预期影响。存在索引不等于索引路径更便宜。

### 一次执行看到的是一个快照

普通查询读取符合当前快照的行版本。默认 Read Committed 下，每条语句开始时取得新快照；同一事务中连续执行两条相同查询，结果可能不同。这与 MySQL/InnoDB 常见的默认行为并不一致。

可以从一开始就养成查看真实计划的习惯：

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)
SELECT id, title
FROM article
WHERE author_id = 42
ORDER BY published_at DESC
LIMIT 20;
```

`ANALYZE` 会真正执行语句。对写语句或高成本查询使用它之前，必须确认影响范围；必要时放在事务中执行并回滚，但要注意序列、外部副作用和锁并不会都被“无痕撤销”。

**本章结论**：分析 PostgreSQL 问题时，至少区分连接、规划、执行、缓存和事务快照五个层次。把所有问题都归结为“索引没生效”，通常会错过真正原因。

**思考题**：同一 SQL 使用预编译语句后计划变差，问题最可能发生在上述哪个阶段？

## 第 2 章：实例、数据库、模式和用户到底是什么关系？

MySQL 中的 `database` 常被当作逻辑命名空间使用。在 PostgreSQL 中，最接近这个概念的是 `schema`，而 PostgreSQL 的 `database` 是更强的隔离边界。

一个 PostgreSQL 实例管理一个数据库集群。集群中可以有多个 database；每个 database 内有多个 schema；表、视图、函数和类型等对象位于 schema 中。一个普通连接只能连接一个 database，不能用 `db_a.table_x` 直接跨库查询 `db_b`。

```text
实例（cluster）
├── database: app_prod
│   ├── schema: public
│   ├── schema: billing
│   └── schema: audit
└── database: analytics
```

如果只是为了区分业务模块或租户，优先考虑 schema，而不是创建大量 database。跨库确有需要时，可以使用 `postgres_fdw` 等机制，但这已经引入了远程访问、事务边界和故障处理问题。

### 用户和角色是同一个系统

PostgreSQL 使用 role 统一表示用户与角色。带 `LOGIN` 属性的 role 可以登录，不带 `LOGIN` 的 role 常用于权限分组。

```sql
CREATE ROLE app_rw NOLOGIN;
CREATE ROLE app_user LOGIN PASSWORD 'replace_me';
GRANT app_rw TO app_user;

GRANT USAGE ON SCHEMA billing TO app_rw;
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA billing TO app_rw;
```

只授权已有表还不够。未来创建的对象受默认权限控制，且默认权限属于“创建对象的角色”：

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE ddl_owner IN SCHEMA billing
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
```

### `search_path` 既方便，也可能制造风险

未带 schema 的对象名按 `search_path` 查找。生产代码最好固定搜索路径，关键对象使用限定名。若把允许普通用户创建对象的 schema 放在前面，可能发生对象遮蔽。

```sql
SET search_path = billing, pg_catalog;
SELECT * FROM invoice;
-- 等价目标应明确为 billing.invoice
```

**本章结论**：MySQL database 通常映射为 PostgreSQL schema；登录身份与权限组都由 role 表示；对象所有者、对象权限和默认权限是三件不同的事。

## 第 3 章：从 MySQL 迁移时，哪些类型和 SQL 最容易埋雷？

迁移工具可以转换表结构，却不能替你判断业务语义。最危险的差异集中在布尔值、时间、字符排序、数值和空值处理上。

### 类型不要按名字机械映射

| MySQL 常见写法 | PostgreSQL 建议 | 注意点 |
|---|---|---|
| `tinyint(1)` | `boolean` | 不再用 0/1 混合表示状态 |
| `int unsigned` | 更大有符号类型或 `CHECK` | PostgreSQL 整数没有 `unsigned` |
| `datetime` | `timestamp` | 不包含时区语义 |
| `timestamp` | 常为 `timestamptz` | 存储时刻，显示时按会话时区转换 |
| `longtext` | `text` | PostgreSQL 的 `text` 无需指定长度 |
| `json` | `jsonb` 或 `json` | `jsonb` 可索引并规范化存储；原始文本保真需求用 `json` |
| `enum` | 枚举、字典表或 `CHECK` | 取决于值是否频繁变化 |
| `blob` | `bytea` | 大对象 API 是另一套机制 |

金额应优先使用 `numeric(p,s)`，不要使用浮点数。业务时刻通常用 `timestamptz`，门店“每天 09:00 营业”这类墙上时间才是 `time` 或不带时区的时间概念。

### 大小写和引号规则不同

PostgreSQL 会把未加双引号的标识符折叠为小写：

```sql
CREATE TABLE UserProfile (UserId bigint);
-- 实际对象名是 userprofile，列名是 userid
```

如果创建 `"UserProfile"`，以后每次引用都必须保留双引号和大小写。迁移时统一改成小写蛇形命名，通常比长期背负引号更稳妥。

字符串使用单引号，标识符使用双引号。不要延续 MySQL 某些模式下把双引号当字符串引号的习惯。

### 隐式转换没有想象中宽松

PostgreSQL 更强调类型明确。把整数列与文本参数比较、把空字符串写入数值列，常会直接报错。这样做会增加迁移工作量，却能更早暴露数据污染。

```sql
-- 推荐让参数本身就是 bigint；必要时显式转换
SELECT * FROM orders WHERE customer_id = $1::bigint;
```

`NULL` 仍然表示未知。`col = NULL` 永远得不到真，应使用 `IS NULL`；需要把 `NULL` 当作可比较值时，可使用 `IS DISTINCT FROM`。

### 排序规则会影响唯一性和索引

字符比较结果取决于 collation。迁移前必须验证大小写、重音符号、中文排序和尾随空格的行为。不要假设 MySQL 原有 collation 与 PostgreSQL 目标环境等价。需要大小写不敏感搜索时，可评估规范化列、表达式索引或 `citext` 扩展。

**本章结论**：先迁移语义，再迁移类型。类型越明确，后续索引、约束和查询计划越可靠。

**思考题**：一个字段同时保存 `0`、`1`、空字符串和 `NULL`，迁移为 `boolean` 前应先确定哪些业务规则？

## 第 4 章：自增、UPSERT 和返回值，为什么值得重新设计？

MySQL 应用常依赖 `AUTO_INCREMENT` 和 `LAST_INSERT_ID()`。PostgreSQL 更适合把“编号生成”和“插入后返回数据”分开理解。

### 优先使用 identity，而不是把 serial 当作类型

`serial` 是创建整数列、序列和默认值的历史简写；identity 是标准化、依赖关系更清楚的表达。

```sql
CREATE TABLE account (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

序列不是无间隙计数器。事务回滚、缓存和并发都会留下空洞。订单展示编号若要求连续，必须单独建模，并接受更强的串行化成本。

### 用 `RETURNING` 获取数据库最终写入的值

```sql
INSERT INTO account (email)
VALUES ('reader@example.com')
RETURNING id, created_at;
```

`INSERT`、`UPDATE`、`DELETE` 和 `MERGE` 都可返回受影响行。这样可以直接拿到默认值、生成列或触发器处理后的结果，避免再发一次查询。

### UPSERT 的关键是冲突目标

```sql
INSERT INTO account (email)
VALUES ($1)
ON CONFLICT (email) DO UPDATE
SET last_seen_at = now()
RETURNING id;
```

`ON CONFLICT` 依赖唯一约束或唯一索引来定义冲突。不要把任意查询条件误当作冲突目标，也不要用“先查再插”替代原子操作，否则并发下仍会重复。

更新时可以引用待插入行：

```sql
INSERT INTO inventory (sku, quantity)
VALUES ($1, $2)
ON CONFLICT (sku) DO UPDATE
SET quantity = inventory.quantity + EXCLUDED.quantity;
```

这条语句仍需考虑锁等待和死锁。如果一次处理多个 SKU，所有事务应采用稳定顺序。

**本章结论**：identity 负责生成候选编号，唯一约束负责判定冲突，`RETURNING` 负责返回最终结果。三者职责不同。

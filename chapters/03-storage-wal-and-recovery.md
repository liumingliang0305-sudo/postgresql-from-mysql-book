# 第三部分：存储、日志与恢复

## 第 10 章：表不是按主键组织的，会带来什么变化？

InnoDB 的主键索引组织表让很多 MySQL 开发者形成一个直觉：通过主键查到叶子节点，也就拿到了整行。PostgreSQL 的普通表是 heap，索引项通常保存键值和行版本的物理位置 `ctid`。索引扫描先找到 `ctid`，再到堆页读取元组并判断可见性。

这会带来三项重要差异。

### 主键只是一个唯一索引，不决定表的永久顺序

```sql
CREATE TABLE orders (
    id bigint PRIMARY KEY,
    created_at timestamptz NOT NULL,
    payload jsonb NOT NULL
);
```

这里的主键会创建唯一 B-tree 索引，但 heap 不会持续按 `id` 排列。`CLUSTER` 可以按某个索引一次性重写和排序表，却不会在后续写入时自动维持顺序。

因此，没有 `ORDER BY` 的查询永远不保证结果顺序；顺序扫描与索引扫描切换后，返回顺序尤其可能变化。

### Index-only scan 也要确认可见性

即使查询列都在索引中，执行器仍需知道行版本对当前快照是否可见。可见性映射标记某个堆页是否“全部可见”；只有相关页面满足条件时，index-only scan 才能少访问 heap。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE created_at >= now() - interval '1 day';
```

计划中的 `Heap Fetches` 很高，往往说明大量页面尚不能只靠可见性映射确认。频繁更新、VACUUM 不及时或查询刚写入的数据，都可能造成这种现象。

### 大字段可能被 TOAST 拆出去

页面大小有限，宽值可能被压缩或存入关联的 TOAST 表。读取只涉及窄列时，不一定会加载完整大字段；但频繁返回大 JSON、长文本或二进制值，仍会产生解压、额外页面访问和网络传输成本。

不要因为 PostgreSQL 支持 `text` 和 `jsonb` 就把所有属性塞进一个超宽行。冷热字段、访问模式和更新频率仍应参与建模。

### 页面空间由两张辅助地图描述

Free Space Map 记录页面可用空间，帮助插入和更新寻找位置；Visibility Map 记录页面是否全部可见、是否全部冻结。前者影响写入位置，后者影响 VACUUM 和 index-only scan。

**本章结论**：PostgreSQL 的索引与 heap 相互独立，MVCC 可见性判断贯穿读取过程。理解 `ctid`、可见性映射和 TOAST，才能解释随机 I/O、回表和宽行成本。

**思考题**：某查询明明显示 `Index Only Scan`，为什么执行计划仍可能出现大量 heap fetch？

## 第 11 章：WAL 怎样保证提交过的数据不会丢？

把每个被修改的数据页在提交时同步写回磁盘，代价很高。PostgreSQL 使用 Write-Ahead Logging：先把描述修改所需的信息持久化到 WAL，再允许相应数据页稍后写回。

“先写日志”有严格顺序：某个数据页落盘前，与该修改相关的 WAL 必须先刷到稳定存储。实例崩溃后，PostgreSQL 从最近检查点开始重放 WAL，把尚未写入数据文件的修改恢复出来。

### COMMIT 等待的是什么

在常见配置下，事务提交需要等待相关 WAL 刷盘，而不是等待所有脏数据页写回。多个事务可以共享一次 WAL 刷盘，形成组提交。

`synchronous_commit = off` 可以减少提交等待，但最近一小段已报告成功的事务可能在数据库或操作系统崩溃时丢失。它不会把数据库结构破坏为半个事务，却改变了“成功返回就一定持久化”的承诺。只有明确允许少量数据丢失的工作负载才应使用。

`fsync`、`full_page_writes` 和 WAL 相关安全参数不是普通性能开关。关闭前必须理解存储栈的持久性语义和故障后果。

### 为什么会有完整页镜像

操作系统崩溃可能造成 torn page：一个数据页只写入一部分。默认开启 `full_page_writes` 时，检查点后的首次页面修改会把页面完整镜像写入 WAL，使恢复过程能够修复不完整页面。

这也解释了一个现象：检查点后写入负载的 WAL 量可能暂时上升。页面首次被修改需要完整页镜像，后续修改通常只记录增量 WAL，直到下一个检查点重新开始。

### WAL 不只服务于崩溃恢复

同一条 WAL 链还支撑：

- 流复制；
- 持续归档与时间点恢复；
- 逻辑解码所需的变更信息；
- 某些备份与增量恢复能力。

因此，WAL 生成过快可能同时影响磁盘、归档、网络、备库和复制槽。诊断写入压力时，只看数据目录增长是不完整的。

**本章结论**：事务持久性依赖 WAL 先行，而不是数据页立即落盘。任何降低 WAL 安全性的调优，都等价于修改故障承诺。

**思考题**：把 `synchronous_commit` 关闭后，为什么实例重启通常仍能保持事务原子性，却可能丢失已经返回成功的事务？

## 第 12 章：检查点为什么会制造 I/O 压力？

WAL 可以不断记录变化，但崩溃恢复不能永远从很早的位置开始。检查点建立一个新的恢复起点：把检查点之前相关的脏页逐步刷入数据文件，并在 WAL 中记录检查点信息。

检查点过于频繁会带来三类成本：脏页更集中地写回；完整页镜像更频繁出现；存储缓存和后台写入器承受更大波动。检查点间隔太长则会增加 WAL 保留和恢复时间，并在最终刷盘时形成更大工作量。

### 两个触发方向

检查点既可能按时间触发，也可能因为 WAL 增长达到上限而触发。若日志频繁出现“checkpoints are occurring too frequently”，通常说明 `max_wal_size` 与写入速率不匹配，或者批量任务生成 WAL 过快。

`checkpoint_completion_target` 让检查点写入尽量铺开到周期的大部分时间，目的是平滑 I/O，而不是减少必须写的数据总量。

### 强制 CHECKPOINT 不是常规维护动作

```sql
CHECKPOINT;
```

该命令要求较高权限，并会立即推动检查点工作。它适用于少数受控场景，不应作为“释放内存”或“让数据落盘”的日常命令。PostgreSQL 已有自己的检查点和缓冲区管理机制。

### 观察而不是猜测

新版本统计视图能够展示检查点、后台写入与后端写入活动。分析时至少关联以下信号：

- 检查点是按时触发还是 WAL 压力触发；
- 检查点写入与同步耗时；
- WAL 生成速率；
- 存储延迟和队列；
- 业务延迟尖峰是否与检查点时间重合。

如果大量脏页由业务后端自己写出，说明后台平滑写入可能跟不上；如果检查点同步时间很高，则要检查存储持久化延迟，而不只是调数据库参数。

**本章结论**：检查点是在恢复时间、WAL 空间和前台 I/O 之间做平衡。调优目标是平滑并可预测，不是让检查点消失。

**思考题**：增大 `max_wal_size` 可能降低检查点频率，但会给恢复和磁盘容量带来什么变化？

## 第 13 章：备份、归档和 PITR 应该怎样组合？

“每天执行一次 `pg_dump`”不是完整的恢复策略。先定义恢复目标：允许丢多少数据，即 RPO；允许停多久，即 RTO。工具选择必须服从目标。

### 逻辑备份适合对象级迁移，不等于连续恢复

`pg_dump` 导出数据库对象和数据，适合版本迁移、选择性恢复、小中型数据库和结构审计。它生成逻辑内容，恢复时需要重新建表、加载数据和创建索引，时间可能很长。

```bash
pg_dump --format=custom --file=booklab.dump booklab
pg_restore --list booklab.dump
```

`pg_dump` 能获得一致性视图，不需要把数据库锁成只读；但它只覆盖一个 database，集群级角色和表空间等对象要另外处理。备份文件存在并不代表可恢复，必须定期做隔离恢复演练。

### 物理基础备份加 WAL 归档才能做 PITR

时间点恢复的基本组合是：

```text
一个可用的物理基础备份
        +
从备份开始连续且完整的 WAL 归档
        =
可恢复到覆盖范围内的目标时间点
```

恢复时先还原基础备份，再重放归档 WAL，直到目标时间、事务号或恢复点。只保留 WAL 而没有对应基础备份不够，只保留基础备份则最多恢复到备份时刻。

### 备份链必须能证明完整

至少验证：

1. 基础备份校验通过；
2. WAL 归档没有缺口；
3. 加密密钥、配置和权限文件可获得；
4. 恢复环境有足够容量；
5. 能在目标时间内启动并通过业务校验；
6. 恢复流程不会误连生产写入端。

恢复演练应记录实际耗时和人工步骤。没有演练过的 RTO 通常只是愿望。

**本章结论**：逻辑备份解决可移植和对象级恢复，物理基础备份加连续 WAL 解决快速恢复与 PITR。生产系统通常需要二者互补。

**思考题**：基础备份每天一次，WAL 连续归档。某天 15:00 误删数据，为什么可以恢复到 14:59，而不必退回当天凌晨？

## 第 14 章：复制延迟只看一个数字为什么不够？

物理流复制传输 WAL。主库生成 WAL，发送端传输；备库接收、写入、刷盘并重放。所谓“延迟”至少分成生成、传输、落盘和重放几个阶段。

主库可以从 `pg_stat_replication` 观察各阶段 LSN：

```sql
SELECT application_name,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn,
       write_lag,
       flush_lag,
       replay_lag
FROM pg_stat_replication;
```

如果 `sent_lsn` 已接近主库当前位置，而 `replay_lsn` 落后，问题更可能在备库重放；如果发送本身落后，要检查网络、WAL sender 和复制槽状态。时间型 lag 字段并非所有时刻都代表“当前还差多少”，空闲系统尤其要结合 LSN 差值和最后重放时间判断。

### 同步复制保证到哪一层

同步备库可以让主库提交等待远端接收、写入、刷盘，甚至重放到可查询状态，具体取决于配置。保证越强，提交延迟越依赖网络和备库。

如果同步备库不可用，主库可能阻塞提交。高可用设计必须明确：此时优先数据零丢失，还是优先主库继续写入。这个选择不能交给故障发生时临时决定。

### 复制槽既保护消费者，也保护磁盘占用

复制槽会阻止主库删除消费者仍需要的 WAL；逻辑复制槽还可能保留清理所需的信息。消费者长时间停止，槽会让 `pg_wal` 持续增长，甚至占满磁盘。

```sql
SELECT slot_name,
       slot_type,
       active,
       restart_lsn,
       confirmed_flush_lsn,
       wal_status
FROM pg_replication_slots;
```

因此，每个槽都必须有明确的消费者、容量上限、告警和下线流程。删除槽会放弃其保留位置，属于需要确认后果的操作。

### 热备查询也会与恢复冲突

备库上的长查询可能需要主库已经删除的旧版本。系统要么取消备库查询以继续重放，要么通过反馈让主库延迟清理，从而增加主库膨胀风险。`hot_standby_feedback` 不是免费开关，它把冲突从备库查询转移到主库版本回收。

**本章结论**：复制延迟是一条流水线，不是一个数字。诊断时要先定位 WAL 停在哪个阶段，再判断是容量、网络、I/O、重放还是查询冲突。

**思考题**：开启 `hot_standby_feedback` 后备库查询更稳定，为什么主库 dead tuple 可能开始增加？
